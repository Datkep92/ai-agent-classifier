1. BUG REPORTED AND FIXED
Symptom: pasting a key produced no tree at all. The key stayed in
Unresolved and never appeared under the provider.

Root cause: resolveUnresolved() only handled MODEL items. Every
API_KEY item hit an early `kept.push(item); continue;` and was never
retried, so a key pasted before its provider could never bind to it.

Fixes in core/mapper.js:
- API_KEY items are now scanned against every known provider.
- A cheap discovery call authenticates the key before any inference
  request is spent.
- A key rejected by one provider is retried against the next instead of
  being declared dead, because AUTH_INVALID is only valid for that
  provider.
- A key that authenticates but advertises no models is still attached
  to the provider (AUTH_OK_NO_MODELS) so it is visible in the tree.
- A model that no provider advertises is now probed directly instead of
  being discarded: not being listed is not proof of being unusable.
  Only a real inference PASS resolves it.

  this, the UI kept rendering the original parked hint, so the inbox

1. WHAT WAS ASKED
1) A model the user pastes must attach to an existing or new URL.
2) On UI startup, load every stored provider's full model list from
   /models, in the background, with progress.
3) When a key is pasted, scan it against all known providers x models
   instead of stopping at the first provider or the first 12 models.

2. DESIGN DECISIONS
- A pasted model is automatically marked favourite, because naming a
  model is a statement of intent. Discovered models can be starred by
  hand with the new star button.
- Two buttons were added: "TAAI LAI MODEL" (force refresh, ignores the
  freshness window) and "KIEM TRA NHANH" (quick test).
- Quick test targets exactly: mappings whose model is starred, plus
  mappings that have never been tested.
- Startup sync skips a provider whose last successful fetch is under
  30 minutes old. Only SUCCESS stamps that timestamp, so a provider that
  failed stays eligible for a retry.
- Import-time probing keeps its existing 12-model cap. Only a
  deliberate key scan uses unlimited models, so pasting stays cheap
  while scanning stays complete.
- Star toggling goes through a dedicated registry method
  (setModelCapabilities) rather than upsertModel. Going through upsert
  recorded the model as "pasted", which made a discovered model claim
  the user had named it.

3. BUGS FOUND BY THE NEW TESTS
The new suite (23 cases) caught four real defects that had been
latent in the in-progress implementation:

(a) Duplicate speculative-attach logic. probeUnknownModel and
    syncPastedModelsToProviders were two copies of the same idea, and
    they had drifted: the rollback that deletes a disproved guess
    existed only in one of them. A model no provider served was rolled
    back and then immediately re-added by the other path, which is
    exactly the "model assigned to the wrong provider" bug reported by
    the user. Fixed by collapsing both into one implementation.

(b) Stale candidates record. The failed-attach branch rewrote the
    parked item with `candidates: probed.attempted`, a field that no
    longer existed after the refactor. The UI therefore showed no
    record of what had been tried. It now re-reads the record the
    helper already wrote.

(c) Freshness timestamp never set. The 30-minute skip keyed off a field
    that nothing ever wrote, so every page load re-fetched every
    provider. discoverProvider now stamps lastSyncedAt on success.

(d) Wrong resolved count. syncAllProviders counted
    resolveUnresolved().resolved.length, but that array also carries
    per-mapping probe results, so the number was meaningless. It now
    measures the actual before/after difference in the inbox.

COP YLOG - CLASSIFIER: STRUCTURAL MODEL vs KEY
Date: 2026-10-06
==================================================

1. THE ASK
"them them logic loai tru so sanh cau truc api voi model la dc"
-> Add a structural discriminator so API keys and model ids are told
   apart by SHAPE, not by keyword list. The open defect was 18/44 models
   correctly classified.

2. METHOD: MEASURE FIRST, THEN RULE
I profiled every corpus value on structural features before writing any
code: segment count, alphabetic vs numeric segments, digit ratio,
unique-char ratio, longest run, Shannon entropy. Every rule below came
from an observed separation, not a guess.

Three failure groups, each with a distinct cause:
(a) read as URL  - gemini-2.0-flash-exp, qwen2.5-coder-32b-instruct,
    phi-3.5-mini-instruct, gpt-4.1-2025-04-14. Cause: the old rule was
    "has dots and no spaces", which every versioned model id satisfies.
(b) read as KEY  - claude-3-5-sonnet-20241022, qwen3-235b-...
    instruct-2507. Cause: a trailing date makes the token look random,
    so the entropy test fired before the model test.
(c) UNKNOWN      - nvidia/Llama-3.1-Nemotron-70B-Instruct-HF. Cause: a
    slash-bearing repo path matched neither branch.

3. THE RULES (core/classifier.js)
- Hostname: the LAST dotted label must be alphabetic. A TLD is letters;
  a model version dot is followed by a number. One rule fixes group (a).
- Model: a token with at least two segments where one segment contains a
  3+ letter word. Requires >1 segment on purpose: a bare English word
  also has a 3-letter run, and without this "some totally unknown
  content" parsed as four models and lost its UNKNOWN status (caught by
  existing test S8).
- Key: an unbroken blob with no separators is a key. Every model id is
  composed; a prefix-free key is not. This catches keys that no prefix
  table can enumerate.
- Key prefix table extended to non-LLM vendors (GitHub, GitLab,
  HuggingFace, Replicate, Stripe, AWS, NVIDIA, Cohere), because those
  payloads contain readable letter runs such as "ghp", "glpat" and
  "live" and are model-shaped by accident.

4. WHAT WAS MEASURED AND REJECTED
Shannon entropy was the obvious discriminator and it does NOT work. Keys
span 3.84-5.14 bits/char but real models reach 4.43
(nvidia/Llama-3.1-Nemotron-70B-Instruct-HF), which is higher than the
weakest real key. Any threshold that catches those keys also destroys
that model. Rejected on evidence, not on taste.

A "real English word" test (case-boundary + vowel check) was also tried
and abandoned: it still flagged glpat/sk_live, and it failed to recognise
gpt-4o, Qwen/Qwen2.5-72B-Instruct and gpt-4.1-2025-04-14.

5. OVER-FIT CHECK (this is the part that matters)
The first working version scored 71/71 on the corpus. Testing against 51
values NOT in the corpus showed only 39/51: six real key formats
(ghp_, glpat-, hf_, r8_, sk_live_, pk_live_) were being read as models,
because their payloads contain letter runs and no vendor prefix was
listed. That gap is exactly what a corpus-only score hides.

After the prefix table and the blob rule, held-out results are 56/56:
35 models, 11 keys, 6 URLs, 4 prose strings. Those 56 values are now
permanent assertions in tests/cases-classifier.js (suite CL2) so a
future change cannot score well by memorising the corpus.

6. TEST RESULTS
- npm test: 103 passed, 0 failed (was 87; 16 new classifier cases).
- node --no-experimental-fetch tests/bench-classifier.js:
  TOTAL 71/71 (100%) - API_KEY 14/14, URL 8/8, UNKNOWN 5/5, MODEL 44/44.
  Previously 45/71 with MODEL 18/44.
- Ingest path re-checked end to end: a mixed paste of URL + labelled
  model + key still classifies as URL / MODEL / API_KEY.
- Held-out (not in corpus): 56/56.

7. SAFETY
core/classifier.js was the file an earlier edit had broken, taking real
key formats with it. This time the change is backed by a benchmark that
must run before AND after, by per-rule assertions, and by a held-out set
chosen to include key formats the corpus does not contain. No existing
key case regressed: 14/14 before, 14/14 after.
